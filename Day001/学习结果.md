## 三、今天学到的内容（详细知识笔记）

### 3.1 Java 线 · JDK 安装、IDEA、第一个 Java 程序

#### 3.1.1 JDK / JRE / JVM 三者关系【能讲清】

**是什么（一句话）**：JDK 是给开发者的完整工具包（编译器 `javac` + 标准类库 + 运行时），JRE 是只用来「跑」Java 程序的运行时环境（核心类库 + JVM），JVM 是真正把字节码翻译成机器指令执行的虚拟机；三者是 **JDK ⊃ JRE ⊃ JVM** 的包含关系。

```
JDK  ── 开发用：javac / jar / javap / jshell + 标准类库 + 运行时
 └─ JRE ── 运行用：标准类库 + JVM（不给编译器）
     └─ JVM ── 执行用：加载 .class、解释 + JIT 编译、内存管理/GC
```

**对比表（满足判断标准「3 条差异 + 各自适用场景」）**：

| 维度 | JVM | JRE | JDK |
| --- | --- | --- | --- |
| 本质 | 一台「虚拟的计算机」，规范 + 实现（如 HotSpot） | JVM + 运行所需核心类库的集合 | JRE + 开发工具（`javac`、`jar`、`javap`…） |
| 能不能编译 `.java` | 不能 | 不能 | 能，`javac` 就在 JDK 里 |
| 能不能运行 `.class` | 能（但需要类库配合，实际由 JRE 提供完整环境） | 能 | 能 |
| 输入 / 输出 | 输入字节码，输出程序行为 | 输入 `.class` + 类库，输出程序行为 | 输入 `.java`，输出 `.class`，再运行 |
| 是否跨平台 | 不同 OS 有不同实现，正是它屏蔽了平台差异 | 分平台 | 分平台 |
| 适用场景 | 讨论执行、GC、内存、性能、字节码版本时 | 只需要运行已有 Java 程序的客户机 / 运行时镜像 | 写代码的开发机、CI 构建机、编译镜像 |
| 本机对应物 | HotSpot 64-Bit Server VM（见 2.1 输出） | 内置于 `D:\JDK` | `D:\JDK`（`java.home`），PATH 里是 javapath 的 `java.exe` / `javac.exe` |

**3 条差异（背这三条就够）**：① 职责不同——JVM 只执行、JRE 只运行、JDK 能开发；② 内容不同——前者是后者的子集，逐层包含；③ 面向的人不同——JVM 面向「程序运行」，JRE 面向「使用者」，JDK 面向「开发者」。

**为什么重要**：装了 JDK 就同时有了 JRE 和 JVM；只装 JRE 能运行但不能编译。今天验收要求 `java -version` 与 `javac -version` 都能输出且版本一致，本质就是在验证「我装的是 JDK，不是只有运行时」（2.1 已通过）。

**怎么用 / 坑**：`java -version` 查运行时，`javac -version` 查编译器；两者版本不一致说明 PATH 指向了不同安装目录。Java 9 之后官方不再单独提供 JRE 安装包，现在常见的是 JDK + `jlink` 定制运行时镜像，所以「JRE 是一份可下载安装包」这个说法在今天**已经不普适**（Q1 的反例）。

**今天的最低要求（详版原问）**：能指着「JDK 安装、IDEA、第一个 Java 程序」里的具体一行说清它在干什么 —— 例：`javac Hello.java` 这一行，用的是 **JDK** 里的编译器；`java Hello` 这一行，用的是 **JRE 中的 JVM**；`System.out.println(...)` 这一行，用的是 JDK 附带的**标准类库**（`java.lang.System`、`java.io.PrintStream`）。

#### 3.1.2 `javac` 编译与 `java` 运行两条命令【能讲清】

**是什么**：`javac` 是 Java 编译器，把人写的 `.java` 源文件翻译成 JVM 能懂的 `.class` 字节码；`java` 是启动器，启动 JVM、加载类、找到 `main` 方法并执行。

**两条命令的完整流程**：

```text
Hello.java  ──javac Hello.java──▶  Hello.class（字节码，与平台无关）
                                      │
                                      └──java Hello──▶ JVM 加载/校验/解释+JIT ──▶ 屏幕输出 Hello, Java
```

```powershell
javac Hello.java     # 【实测】无输出 = 编译成功；目录里多出 Hello.class
java Hello           # 【实测】输出 Hello, Java（注意：不带 .class 后缀）
```

**验证命令（判断标准「说出一条验证命令」）**：`javac -version` 与 `java -version` 双查版本；`Get-ChildItem Hello.class` 确认编译产物存在；`java Hello` 确认字节码可执行；想进一步看字节码内容，用 `javap -c Hello`（本机需先把 `%JAVA_HOME%\bin` 加进 PATH，见 2.2）。

**坑（实测）**：
- `java Hello.class` → `错误: 找不到或无法加载主类 Hello.class / 原因: java.lang.ClassNotFoundException: Hello.class`。因为 `java` 后面要的是**全限定类名**，点号被当成包名分隔符，不是文件名。
- 类名与文件名必须一致：`public class Hello` 必须叫 `Hello.java`，否则编译报 `类 Hello 是公共的, 应在名为 Hello.java 的文件中声明`。
- 中文源码要显式指定编码：`javac -encoding UTF-8 Hello.java`（9.2 案例 ④）。
- 编译与运行的 JDK 版本要匹配：高版本编出来的 `.class` 在低版本 JVM 上跑会 `UnsupportedClassVersionError`，这正是本机 JDK 25 与计划 JDK 21 不一致带来的实际风险（2.3）。

**为什么重要**：理解「先编译再运行」是理解 Java 的第一步，也是它和 Python 最大的区别。编译期能提前抓出语法错和类型错；代价是多一步、多一个产物。

#### 3.1.3 `main` 方法各部分的含义【会用】

> 详版这里只笼统写了「类里的函数，把一段逻辑命名后复用」，这句对**普通方法**是对的，但今天的 `main` 有更精确的含义。把签名逐词拆开才是本知识点真正要会的东西：

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, Java");
    }
}
```

| 片段 | 含义 | 去掉 / 写错会怎样 |
| --- | --- | --- |
| `public class Hello` | 定义一个公共类，类名必须与文件名 `Hello.java` 一致 | 名字不一致 → 编译错误 |
| `public` | 访问修饰符，JVM 从类外部启动入口，必须能访问 | 入口不可见（标准写法要求 public） |
| `static` | 属于类而非对象，JVM 不必先 `new Hello()` 就能调用它 | **【实测】本机 JDK 25 上删掉 `static` 仍能运行并输出**（Java 25 起「实例 main 方法」已可用）；但在计划的 JDK 21 上默认会报 `Main method not found in class ...`。学习/考试一律写标准签名 |
| `void` | 返回值类型：不向 JVM 返回任何值 | 写成 `int` → 不是合法入口 |
| `main` | 固定的入口方法名，JVM 按这个名字找 | 改名 → `Error: Main method not found` |
| `String[] args` | 命令行参数，字符串数组；`java Hello Tom` 时 `args[0] == "Tom"` | 改成 `String args` → 签名不匹配，找不到入口 |
| `{ ... }` | 方法体：程序真正开始执行的地方 | 少一个 `}` → `reached end of file while parsing`（4.2 实测） |
| `System.out.println(...)` | 标准库调用链：`System` 类 → `out` 静态字段（`PrintStream`）→ `println` 方法，输出并换行 | 删掉 → 编译成功、运行无输出（4.2 实测） |

**详版提到的「方法设计原则」也记下来**：一段代码能用一句话说清在干什么，才值得拆成方法；一个方法只做一件事；参数超过 4 个考虑封装成对象。今天的 `main` 就只做一件事：打印一行。

**「会用」的判断标准**：给需求能不看示例写代码 —— 见 Q6 和 8.4（支持命令行输入、加一段判断、抽一个方法）。

├── .idea/                    ← IDEA 自己的配置：编译器设置、运行配置、索引缓存（不用手改，通常不提交）

### 3.2 Python 线 · Python 安装、VS Code、第一个脚本

#### 3.2.1 解释器与脚本文件的关系【会用】

**是什么**：解释器是「逐行读取并执行代码的程序」，脚本文件是「装着代码的纯文本 `.py` 文件」。文件本身什么都不会做，是解释器把它读进去、编译成内部的字节码对象、再执行。

**为什么重要**：Python 没有需要你管理的编译产物，改完直接跑，开发快；代价是类型错误、名字写错这类问题要到**运行到那一行**才暴露（4.3 实测的 `NameError` 就是例子）。

**三种执行方式（对比表，满足「3 条差异 + 适用场景」）**：

| 方式 | 命令 | 输入来自 | 有无 `.py` 文件 | 适用场景 | 代价 / 什么时候不能用 |
| --- | --- | --- | --- | --- | --- |
| 脚本文件 | `python hello.py` | 文件全文 | 有 | 正式代码、可保存可复用可提交 Git、RAG 的 ETL 脚本 | 改一次要重跑一次；文件名/编码不对会失败 |
| 交互式 REPL | `python`（提示符 `>>>`），`exit()` 退出 | 你敲一行执行一行 | 无 | 试一个表达式、查函数用法、临时验证 | 代码不留痕迹，不能复现，不适合写完整程序 |
| 单行 `-c` | `python -c "print('Hello, Python')"` | 命令行字符串 | 无 | 极短的验证（如查版本、查 `sys.executable`） | PowerShell/引号规则复杂，本机就踩了坑（4.3） |

**关系对比表（解释器 vs 脚本文件）**：

| 维度 | 解释器 | 脚本文件 |
| --- | --- | --- |
| 是程序还是数据 | 可执行程序（本机 `D:\msys2\mingw64\bin\python.exe`） | 纯文本数据（`hello.py`） |
| 谁驱动谁 | 主动读取并执行 | 被动被读取 |
| 与平台的关系 | 分平台、分版本（3.11 / 3.14 / CPython / PyPy） | 与平台无关，同一份文件可交给不同解释器 |
| 出错时机 | 解释器版本不对 → 语法/依赖不兼容 | 代码写错 → 运行到该行才报错 |
| 适用场景 | 决定运行环境、装包、被 IDE 选中 | 存代码、进版本库、被调度执行 |

**怎么用 / 坑**：`python script.py` 启动解释器执行脚本；`python` 进入 REPL；`python -c "..."` 跑一行。今天的最低要求是「能指着具体一行说清它在干什么」—— `print("Hello, Python")` 这一行是**脚本内容**，由解释器调用内置函数 `print`，把字符串写到标准输出；`python -V` 里的 `python` 则是**解释器本身**。

#### 3.2.2 `python` 与 `python3` 指向哪个版本【会用】

**这是对照型知识，不背定义，直接列表**：

| 对比维度 | `python` | `python3` | `py`（Windows 启动器） |
| --- | --- | --- | --- |
| 典型指向 | 看 PATH 第一个命中；Linux 老系统可能是 2.7 | 明确指向 3.x | 按 `py -3.11` 精确选版本 |
| 本机实测 | `D:\msys2\mingw64\bin\python.exe` → 3.14.7 | `D:\msys2\mingw64\bin\python3.exe` → 3.14.7，另有 WindowsApps 别名 | `py -0p` 列出 3.14（`D:\py3.14.7`）和 uv 的 3.12.14；`py -3.12 -V` 却报 `No suitable Python runtime found` |
| 适用场景 | 明确只有一套 Python 时最省事 | 多版本共存的 Linux/macOS 上避免误用 2.x | Windows 多版本共存时最可靠 |
| 代价 | 容易被 PATH 顺序劫持（本机被 msys2 抢先） | 在 Windows 上可能命中 Microsoft Store 的**占位别名**（打开商店而不是运行） | 需要记住 `-3.11` 这样的参数 |
| 什么时候不能用 | PATH 里有多个 Python 时不能盲信 | 系统没提供该命令时不能用 | 该版本没注册到 py 时不能用（本机 3.12 就是例子） |
| 查证命令 | `where.exe python` + `python -c "import sys; print(sys.executable)"` | `where.exe python3` + `python3 -V` | `py -0p` |

**本机结论**：`python` 和 `python3` 都指向同一套 MSYS2 的 Python 3.14.7；而 `pip` 命令来自另一套 `D:\py3.14.7`。所以「版本号」这道题不能只看 `python -V`，**必须看 `sys.executable`**，它才是真正被使用的解释器路径。

**验证（详版原问「能说出如果我选错了会怎样」）**：见 8.5，本机实测 `python -m pip -V` → `No module named pip`，是最直接的答案。

#### 3.2.3 `pip` 与 `venv` 的作用【会用】

| 概念 | 是什么 | 解决什么问题 | 常用命令 |
| --- | --- | --- | --- |
| `pip` | Python 的包管理器，从 PyPI 下载并安装第三方库 | 不用自己造轮子；同时管理版本与依赖 | `python -m pip install requests`、`python -m pip list`、`pip freeze > requirements.txt`、`pip install -r requirements.txt` |
| `venv` | 标准库自带的虚拟环境，给每个项目一份独立的解释器副本 + `site-packages` | 项目 A 要 `fastapi==0.100`、项目 B 要 `fastapi==0.115` 时，装到全局必然冲突 | `python -m venv .venv` → 激活 → `python -m pip install ...` |

**Windows 激活方式**：

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1       # PowerShell；CMD 用 .\.venv\Scripts\activate.bat
python -c "import sys; print(sys.executable)"   # 应指向 ...\.venv\Scripts\python.exe
python -m pip install requests
python -m pip freeze > requirements.txt
deactivate
```

**为什么重要**：不同项目依赖版本冲突时，虚拟环境是唯一干净解法；**别把包装进系统 Python**。后面 D40「虚拟环境与依赖管理」、D61 之后装 OpenAI SDK / FastAPI / pypdf / pgvector 全靠这一层。

**关键习惯**：一律用 `python -m pip`，而不是裸 `pip`。因为 `python -m pip` 保证「装到当前这个解释器里」；裸 `pip` 可能指向别的安装（本机 `pip` 在 `D:\py3.14.7`、而 `python` 在 `D:\msys2\...`，见 2.2）。本机 `python -m pip` 之所以报错，恰恰证明这个习惯能第一时间暴露错配。

**给一个需求的调用代码（判断标准）**：见 8.4 第 3 题「为一个新项目建独立环境并装一个包」。

#### 3.2.4 VS Code 选择解释器【了解即可】

- **是什么**：VS Code 本身不带 Python，它只是调用某个解释器。选解释器 = 告诉编辑器用哪一个 `python.exe` 来运行、补全、查依赖。
- **去哪查 / 怎么做**：`Ctrl+Shift+P` → `Python: Select Interpreter` → 选带 `.venv` 的那一项；右下角状态栏会显示 `3.11.x ('.venv': venv)`；也可以在 `.vscode/settings.json` 里写 `"python.defaultInterpreterPath": "${workspaceFolder}/.venv/Scripts/python.exe"`。
- **不混淆概念**：Python 扩展（Editor 插件）≠ 解释器（真正跑代码的程序）≠ 虚拟环境（隔离的目录）≠ 终端（只是敲命令的壳）。
- **典型症状**：终端里 `python script.py` 能跑、编辑器里 `import requests` 画红线 → 十有八九是 IDE 选了另一个解释器；对照 `sys.executable` 即可（3.2.2）。
- 层级是「了解即可」，见过、知道去哪查就够了，今天不背配置项。

### 3.3 两条执行链路与差异表（对照重构，≥3 行）

**Java**：`.java` 源码 → `javac` 编译 → `.class` 字节码 → `java` 启动 JVM → 类加载/校验 → 解释 + JIT → 输出。
**Python**：`.py` 源码 → `python` 解释器读取 → 内部编译为字节码对象（内存/`.pyc` 缓存，不由你管理）→ 逐条执行 → 输出。

| # | 维度 | Java | Python | 差异说明了什么 |
| --- | --- | --- | --- | --- |
| 1 | 编译步骤 | 显式 `javac`，产出可见的 `.class` 文件 | 隐式，通常看不到产物 | 语言「编译型 / 解释型」的分界其实在「谁负责这一步」 |
| 2 | 程序骨架 | 必须 `public class Hello` + `public static void main(String[] args)` | `print("Hello, Python")` 一行就是完整程序 | 静态结构成本不同，HelloWorld 行数 5 : 1 |
| 3 | 类型系统 | 静态：`String[] args` 声明了类型，编译期检查 | 动态：`print` 接受任何对象，运行期才报错 | 错误暴露时机不同（4.3 的 `NameError`） |
| 4 | 输出写法 | `System.out.println(...)`，类 → 静态字段 → 方法 | `print(...)`，内置函数 | 命名空间与标准库组织方式不同 |
| 5 | 分块与结束符 | `{ }` 包体，语句以 `;` 结尾 | 缩进分块，换行即结束 | 语法风格；少一个 `}` 直接编译失败（4.2） |
| 6 | 文件命名 | 公共类名必须等于文件名 | 文件名随意（避免与标准库同名） | 编译器约束 vs 约定 |
| 7 | 运行命令 | `javac Hello.java` 然后 `java Hello`（不带后缀） | `python hello.py`（带后缀） | 一个是类名，一个是文件路径 |
| 8 | 环境依赖 | JDK / JRE / JVM 三层 + PATH + JAVA_HOME | 解释器 + pip + venv + IDE 选解释器 | 两边都要能定位「到底在用哪一个」 |

> 差异共 8 行 ≥ 3 行，满足详版「对照重构：抽共同逻辑，记录 3 处 API 差异」；共同逻辑是：**都把人写的文本交给一个运行时程序，运行时把代码变成机器能执行的动作，最后写到标准输出**。

### 3.4 一分钟记忆卡片

- Java：`**JDK ⊃ JRE ⊃ JVM**`；`javac` 造 `.class`，`java` 跑它（不带后缀）；入口固定 `public static void main(String[] args)`。
- Python：解释器读脚本，`python -V` 看版本，`sys.executable` 看真身；`python -m pip` 装包，`venv` 隔离；IDE 里选对解释器。
- 通用：**先看版本号和路径，再看代码**。今天一半的问题都不在代码里。

## 四、代码精读与「改三处」实测记录

### 4.1 逐行读法：每问三个问题（输入什么 / 改了什么状态 / 输出到哪）

Java 版：

| 行 | 输入 | 改了什么状态 | 输出到哪 |
| --- | --- | --- | --- |
| `public class Hello {` | 无 | 声明一个类型 | 无 |
| `public static void main(String[] args) {` | JVM 传入命令行参数数组 `args` | 定义入口，进入方法栈帧 | 无 |
| `System.out.println("Hello, Java");` | 字符串常量 `"Hello, Java"` | 标准输出流被写入一行 | 控制台/终端 |
| `}` `}` | 无 | 方法、类结束，程序退出 | 无 |

Python 版：`print("Hello, Python")` —— 输入是字符串对象；不改程序状态（只写标准输出）；输出到控制台；函数返回 `None`。

### 4.2 Java「改三处」【实测】

**① 换一个输入值**：

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, Day001");
    }
}
```

`javac Hello.java; java Hello` → `Hello, Day001`。说明：`println` 的参数就是输出内容，改字符串即改结果。

**② 删掉一行，看报错信息**：

- 删 `System.out.println("Hello, Java");` → `javac NoPrint.java` **成功**，`java NoPrint` **无输出、无报错**。原因：空方法体是合法程序，编译期不关心「有没有打印」。这告诉我们：**不是所有「删行」都会报错，报错类型取决于删的是语法结构还是执行语句**。
- 删掉结尾两个 `}` → `BadBrace.java:3: error: reached end of file while parsing` / `1 error`。原因：解析器读到文件末尾仍没等到闭合花括号，属**编译期语法错**，`javac` 不会生成 `.class`。
- 删 `static`（改成 `public void main`）→ **本机 JDK 25 上仍编译并输出 `x`**。原因：JDK 25 起支持「实例 main 方法 / compact source file」，JVM 会自己实例化类再调用；**在计划要求的 JDK 21 上默认会报 `Main method not found`**。结论：学习和面试一律用标准签名，别靠新版本特性「碰巧跑通」。

**③ 加一个小功能（不看示例自己写）**：

```java
public class Hello {
    public static void main(String[] args) {
        String name = args.length > 0 ? args[0] : "Java";
        System.out.println("Hello, " + name);
    }
}
```

【实测】`java Hello Tom` → `Hello, Tom`；`java Hello`（不带参数）→ `Hello, Java`。新增了参数读取 + 边界判断，仍是「一个方法只做一件事」的范围内。

### 4.3 Python「改三处」【实测】

**① 换一个输入值**：`print("Hello, Day001")` → `python hello.py` → `Hello, Day001`。

**② 删掉一行**：把文件清空（删掉唯一的 `print`）→ `python empty.py` **无任何输出、无报错、正常退出**。原因：空文件是合法的 Python 程序。对照 Java 删 `}` 会编译失败 —— 这就是「解释执行、运行期才发现问题」和「编译期先检查结构」的直观差别。

**③ 加一个小功能**：

```python
import sys

name = sys.argv[1] if len(sys.argv) > 1 else "Python"
print(f"Hello, {name}")
```

【实测】`python hello.py Tom` → `Hello, Tom`；不带参数 → `Hello, Python`。

**额外踩到的一个真实报错（很有价值）**：

```powershell
python -c 'print("Hello, Python")'
```

```text
Traceback (most recent call last):
  File "<string>", line 1, in <module>
    print(Hello, Python)
          ^^^^^
NameError: name 'Hello' is not defined
```

原因：PowerShell 把外层单引号剥掉后，双引号没传给 Python，Python 收到的是 `print(Hello, Python)`，把 `Hello` 当成变量名 → `NameError`。改成 `python -c "print('Hello, Python')"`（外双内单）或写成 `.py` 文件，【实测】都输出 `Hello, Python`。这条完整演示了详版第九节的排查顺序：**读完整报错 → 定位到行 → 最小复现 → 再改**。

### 4.4 最小可运行示例（抄 + 默写用）

```java
// Hello.java —— 文件名必须与类名一致
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, Java");
    }
}
```

```python
# hello.py
print("Hello, Python")
```

```powershell
javac Hello.java; java Hello      # 【实测】Hello, Java
python hello.py                   # 【实测】Hello, Python
```

### Q1｜用一句话解释「JDK / JRE / JVM 三者关系」，并给一个它不适用的情况。

**一句话**：JDK 是开发工具包（含编译器 `javac` 和标准类库），JRE 是只用于运行 Java 程序的运行时（核心类库 + JVM），JVM 是真正执行字节码的虚拟机，三者是 **JDK 包含 JRE、JRE 包含 JVM** 的逐层包含关系，分别面向「写代码的人」「跑程序的人」「程序执行的那一刻」。

**为什么这么定义（说清它解决什么问题）**：它把「开发」「运行」「执行」三件事分层，所以才能解释「为什么装了 JDK 就既能编译又能运行，而只有运行时环境就只能跑」、也才能解释「同一份 `.class` 为什么能在 Windows / Linux 上跑」—— 因为各平台的 JVM 实现屏蔽了差异。

**不适用的情况（具体反例，给 3 个）**：
1. **Java 9 之后官方不再单独发布 JRE 安装包**。现在部署常用 JDK + `jlink` 定制的运行时镜像或容器基础镜像，所以「JRE 是一份可以下载安装的独立软件」这个说法已经过时；包含关系在概念上仍成立，但产品形态变了。
2. **GraalVM Native Image / 提前编译（AOT）**：可以把 Java 程序直接编译成平台相关的可执行文件，运行时不再需要 JVM，「Java 一定跑在 JVM 上」不成立。
3. **单文件源码模式**：`java Hello.java`（JDK 11+）会在内部隐式编译后直接执行，用户看不到 `javac` 这一步，所以「必须先手动编译出 `.class` 才能运行」这个流程性结论不是绝对的（概念仍对，流程被工具省略）。

### Q2｜「JDK / JRE / JVM 三者关系」和「javac 编译与 java 运行两条命令」有什么区别？各自什么时候用？

这两者不是同类东西：前者是**组件/概念模型**（回答「装了什么、谁包含谁」），后者是**操作流程**（回答「源码怎么变成运行中的程序」）。用一张 6 维表说清：

| 维度 | 三者关系 | 两条命令 |
| --- | --- | --- |
| 语义 / 抽象层 | 静态的层次结构：工具包 → 运行时 → 虚拟机 | 动态的时间顺序：编译期 → 运行期 |
| 回答的问题 | 我该装什么？为什么 `java` 和 `javac` 会同时出现？ | 我该敲什么？为什么有 `.class` 文件？ |
| 使用时机 | 装环境、选 Docker 基础镜像、排查版本不兼容、理解报错归属 | 每写完/改完一次 `.java` 就要重新 `javac`，之后可多次 `java` |
| 性能含义 | 与性能无关（结构描述） | `javac` 只做一次；`java` 每次启动 JVM，运行期 JIT 把热点字节码编译成本地代码，所以「编译一次、到处运行、越跑越快」 |
| 可观察结果 | `java -version` / `javac -version` / `java.home` | `Hello.class` 是否生成、屏幕输出什么、是否抛异常 |
| 使用场景 | 决定开发机装 JDK、客户机/容器只放运行时；解释 `UnsupportedClassVersionError` | 命令行验证、CI 构建脚本、IDEA 的 Build/Run 背后做的事 |
| 什么时候用不上 | 它不告诉你任何一条命令怎么敲 | 它不解释为什么换台机器还能跑、也不解释 JDK 里有什么 |

**一句话收尾**：三者的关系是「地图」，两条命令是「按地图走的路线」；排查环境问题时查地图，写代码跑程序时走路线。例如本机 `javap` 找不到（2.4 问题 2）属于地图问题（PATH 里没放 JDK 的 `bin`），而 `java Hello.class` 报 `ClassNotFoundException` 属于路线问题（命令参数写成了文件名）。

### Q4｜把今天的示例代码删掉一行关键语句，会发生什么？先猜再试。

**先猜**：删 `System.out.println` 应该「什么都不打印但能跑」；删花括号应该「编译失败」；删 `print` 那行 Python 应该「什么都不发生」。

**再试（实测结果，见 4.2 / 4.3）**：

| 删什么 | 语言 | 实际结果 | 报错类型与原因 |
| --- | --- | --- | --- |
| `System.out.println("Hello, Java");` | Java | 编译成功、运行**无输出**，退出正常 | 无报错。方法体为空是合法的，编译期不检查「有没有输出」 |
| 结尾的 `}`（两个） | Java | 编译失败：`BadBrace.java:3: error: reached end of file while parsing`，`1 error` | **编译期语法错误**，解析器未等到类/方法闭合，不生成 `.class` |
| `static` 关键字 | Java | 本机 JDK 25 **仍能运行**并输出 | 版本特性差异（JDK 25 支持实例 main）；JDK 21 上会是 `Error: Main method not found in class NoMain` |
| 唯一一行 `print(...)` | Python | `python empty.py` 无输出、无报错、退出码 0 | 空文件是合法程序，没有语句要执行，因此也不存在运行期错误 |

**结论**：删「执行语句」通常只改变结果（甚至没任何可见变化），删「语法结构」才会在编译期报错；Python 由于没有独立的编译步骤，删行往往连报错都没有，只能靠「没有输出」反推。这也印证了详版说的「结果不对但不报错」要在关键位置打印中间值来定位。

### Q5｜如果遇到「PATH 没配好命令找不到」「Windows 终端中文乱码」「IDEA 首次打开要等索引」，你的排查顺序是什么？

**通用顺序（详版给的骨架：先看报错信息 → 定位到行 → 最小复现 → 再改）**，我把它展开成 6 步：

1. **读完整报错**：不只看第一行，找 `Caused by`、错误类型（`CommandNotFoundException` / `NameError` / `ClassNotFoundException`）、文件名和行号；中文乱码先想办法看到原文（9.2 案例 ④）。
2. **判断属于哪一层**：命令找不到 → PATH/安装层；编译错 → 源码语法层；运行错 → 类路径/解释器/依赖层；结果不对 → 逻辑层；IDE 报红线而命令行能跑 → IDE 配置层。
3. **定位到具体一行 + 最小复现**：把问题压到一个最小文件/一条最短命令上（例如只跑 `java -version`、只跑 `print(1)`）。本次 `NameError` 就是通过「换引号写法」「改写成文件」两种最小复现定位的。
4. **只改一个变量**：一次只改 PATH / 编码 / 引号 / 代码中的一项，改完立刻重测，避免同时改三处不知道是谁起了作用。
5. **按现象查表**（详版第九节）：程序起不来 → 查 PATH 和版本；结果不对不报错 → 打印中间值；照抄示例也跑不通 → 对比版本号、换干净目录；看不懂报错 → 原文 + 语言 + 框架名去搜。
6. **记录 + 40 分钟规则**：把现象、原因、解决写进笔记（本文第十节）；卡超过 40 分钟记进待解决清单继续往下走，周日集中处理。

**分别应用到三个坑**：

- **PATH / 命令找不到**：`where.exe java` / `Get-Command java` 看真实命中 → 检查 PATH 顺序 → 检查 `JAVA_HOME` → 确认 `java -version` 与 `javac -version` 一致 → 重开终端（PATH 不会自动刷新）。本机【实测】`where javap` 找不到，定位为「只配了 javapath、没配 `%JAVA_HOME%\bin`」，见 9.2 案例 ③。
- **中文乱码**：先分清是「自己的程序输出中文乱」还是「工具报错中文乱」。前者：`chcp 65001`、源文件存 UTF-8、`javac -encoding UTF-8`、`$env:PYTHONIOENCODING='utf-8'`；后者：本机【实测】`chcp 65001` 对 `javac` 的中文报错**无效**，改用 `javac '-J-Duser.language=en' '-J-Duser.country=US' BadBrace.java` 输出英文原始报错最省时间（9.2 案例 ④）。

### Q7｜同一件事，Java 和 Python 的写法差在哪？说 2 条。

**① 语法差异（结构成本 + 执行流程）**：Java 必须写 `public class Hello`（且文件名一致）+ `public static void main(String[] args)`，语句用 `;` 结尾、用 `{ }` 分块，还要先 `javac` 再 `java`；Python 一行 `print("Hello, Python")` 就是完整程序，靠缩进分块、换行结束，直接 `python hello.py`。另外输出调用也不同：`System.out.println` 是「类 → 静态字段 → 方法」，Python 的 `print` 是内置函数。

**② 类型系统差异（错误暴露时机）**：Java 静态类型，`String[] args` 明写了参数类型，类型/语法错在 `javac` 阶段就被拦下；Python 动态类型，`print` 接受任何对象，名字写错、类型用错要到运行到那一行才炸 —— 4.3 的 `NameError: name 'Hello' is not defined` 和 4.2 删花括号直接编译失败，正好是两种时机的对照。

**③（补充）产物与运行单位**：Java 留下可见的 `.class` 字节码，`java` 后面跟**类名**；Python 不要求你管理产物，`python` 后面跟**文件路径**。详见 3.3 的 8 行差异表。

### 8.1 费曼输出：用 100 字解释今天最难的一个词，不许用行话

> 选词：**字节码**（不用「编译」「虚拟机」「指令集」这类行话）

你写下的那些英文字母，人看得懂，机器看不懂。所以先请一个「翻译员」把整篇稿子翻成一本薄薄的、格式固定的小册子，里面每一步都写得极短、极整齐。这本小册子不挑电脑：Windows 和 Linux 各有一位「朗读者」，他们照着小册子一句句念出来、指挥电脑干活。好处是稿子只翻译一次，谁都能念；代价是必须先有这本册子，念的人还得看得懂册子的版本。

（对应到术语：`Hello.java` 是稿子，`javac` 是翻译员，`Hello.class` 是小册子，各平台的 JVM 是朗读者；「版本看不懂」就是 `UnsupportedClassVersionError`。）

### 8.2 详版「落地：在示例代码里找出对应一行，注释掉再运行，观察差异」

已在 4.2 / 4.3 执行。这里补一个真正的「注释掉」版本：

```java
public class Hello {
    public static void main(String[] args) {
        // System.out.println("Hello, Java");   ← 注释掉
    }
}
```

编译成功、运行无输出。注：Java 用 `//` 或 `/* */`，Python 用 `#`。注释掉 ≠ 删除，前者保留代码但不执行，适合做「单变量实验」，正是详版第九节要求的排查手法。

### 8.3 详版「验证：想一个反例（什么情况下这句话不成立）」

| 结论型句子 | 反例 / 不成立的情况 |
| --- | --- |
| 「装 JDK 就同时有了 JRE 和 JVM」 | Java 9+ 不再单独发 JRE；用 `jlink` 定制的运行时镜像里可能根本没有 `javac`，此时「JRE 是一个独立存在的目录」这个说法不成立（概念包含关系仍成立） |
| 「Java 一次编译、到处运行」 | 用 JDK 25 编译出的 `.class` 放到只装 JDK 21 的机器上跑 → `UnsupportedClassVersionError`；「到处」的前提是目标 JVM 版本 ≥ 编译版本 |
| 「`main` 必须写成 `public static void main(String[] args)`」 | 本机 JDK 25 实测：去掉 `static` 的实例 main 也能跑（4.2 ②）；Java 25 的 compact source file 甚至可以不写 `public class`。但 JDK 21 / 面试 / 教材仍以标准签名为准 |
| 「一个方法只做一件事」 | 启动类 `main` 常同时做「读配置 + 建容器 + 启动服务」，属于刻意的高层编排；原则是提醒你别把业务细节塞进一个方法，不是硬规则 |
| 「`src` 目录放 `.java`」 | Maven 项目放 `src/main/java`；单文件源码模式连项目目录都不需要（3.1.4） |
| 「`pip install` 装完就能 import」 | 本机实测：`pip` 属于 `D:\py3.14.7`，`python` 属于 `D:\msys2\...`，装完照样 `ModuleNotFoundError`（8.5） |

### 8.5 「能说出『如果我选错了会怎样』」（3.2.2 的验证问）

本机就是活例子：

```text
> where.exe pip
D:\py3.14.7\Scripts\pip.exe
> python -c "import sys; print(sys.executable)"
D:\msys2\mingw64\bin\python.exe
> python -m pip -V
D:\msys2\mingw64\bin\python.exe: No module named pip
```

**选错会怎样**：`pip install requests` 会把包装进 `D:\py3.14.7\Lib\site-packages`，而 `python script.py` 启动的是 `D:\msys2\mingw64\bin\python.exe`，它到自己的 `site-packages` 里找不到 → `ModuleNotFoundError: No module named 'requests'`。更隐蔽的版本是：两套都装了同名包但版本不同，终端能跑、VS Code 画红线，或者行为不一致却完全不报错。

**怎么防**：① 一切装包用 `python -m pip`；② 项目内一律 `venv`，VS Code 选 `.venv`；③ 用 `sys.executable` 而不是 `python -V` 确认真身；④ 提交 `requirements.txt` 让环境和别人一致。

### 9.1 详版第九节排查表（原样 + 本机对应）

### 9.2 本机 6 个真实案例（每个都有实测输出）

1. **`java -version` 显示成红色报错**：`java -version` 把版本写到 **stderr**，Windows PowerShell 5.1 会把 native stderr 包成 `NativeCommandError`（`FullyQualifiedErrorId: NativeCommandError`），看起来像失败。版本信息其实完整输出了。处理：`java -version 2>&1` 或用 PowerShell 7 / CMD。**判断成败要看内容，不要看颜色。**
2. **`python -c` 的 `NameError`**：见 4.3，PowerShell 引号被吞 → `print(Hello, Python)`。处理：外双内单，或写成 `.py` 文件。
3. **`javap` / `jar` 命令找不到**：`where.exe javap` → `INFO: Could not find files`。PATH 里只有 `C:\Program Files\Common Files\Oracle\Java\javapath`（只放 `java.exe`、`javac.exe` 等少数几个），`D:\JDK\bin` 没进 PATH，`JAVA_HOME` 也未设置。处理：设 `JAVA_HOME=D:\JDK`、PATH 加 `%JAVA_HOME%\bin` 并置于 javapath 之前，重开终端。
4. **`javac` 中文报错乱码，`chcp 65001` 无效**：乱码原文实际是「错误: 解析时已到达文件结尾」。`chcp 65001` 让终端按 UTF-8 解码，而 `javac` 输出的是本地 GBK 中文，反而更乱。可靠做法：

   ```powershell
   javac '-J-Duser.language=en' '-J-Duser.country=US' BadBrace.java
   # BadBrace.java:3: error: reached end of file while parsing / 1 error
   ```

   注意 `-J...` 参数**必须加引号**，不加会被 PowerShell 拆开，实测报「无效的标记: .language=en」。另外 `chcp 65001` 该用在「自己的程序输出中文」的场景，配合源文件 UTF-8 保存 + `javac -encoding UTF-8` + `PYTHONIOENCODING=utf-8`。
5. **`python -m pip` 报 `No module named pip`**：见 8.5，解释器与 pip 分属两套安装。处理：venv + `python -m pip`。
6. **删掉 `static` 仍可运行**：JDK 25 的实例 main 特性（4.2 ②）。处理：按计划装 JDK 21，或始终写标准签名；把「本机行为」与「教材结论」的差异记进笔记，别当成自己学会了新写法。

**40 分钟规则**：一个问题卡超过 40 分钟就记进待解决清单继续走，周日集中处理。零基础最常见的失败不是学不会，是被环境问题卡三天 —— 今天上述 6 个坑都在 40 分钟内定位到了层，这也是今天最有价值的成果。

### 今天最大的一个报错

    File "<string>", line 1, in <module>

- **原因**：第一层是 PowerShell 把 `python -c 'print("Hello, Python")'` 的外层单引号剥掉，Python 实际收到 `print(Hello, Python)`，`Hello` 被当成变量名；第二层更本质的是「命令经过了几层壳（编辑器 → 终端 → 解释器）」，每一层都可能改写参数，而我只盯着 Python 代码看。
- **怎么解决的**：按「读完整报错 → 定位到行 → 最小复现 → 单变量改一次」的顺序：先换成 `python -c "print('Hello, Python')"`，再改写成 `hello.py` 文件执行，两次都输出 `Hello, Python`；确认与 Python 语法无关，是终端引号问题。顺手把同类问题（PATH、编码、版本）一并用 `where.exe` / `sys.executable` / 英文 locale 归了层。

### 用我自己的话解释（不看资料）

- **JDK / JRE / JVM 三者关系**：像一套「厨房」。JDK 是整套厨房，既有能把生食材（`.java`）加工成半成品（`.class`）的厨具 `javac`，也有炉子；JRE 是只留了炉子和基础调料、专门用来加热半成品的那部分；JVM 就是那台真正把火候落到菜上的炉子。装了整套厨房，后两样自然都有；只搬来炉子，就只能热别人做好的半成品，自己做不了新菜。
- **解释器与脚本文件的关系**：脚本是一张写着步骤的纸，纸自己不会动；解释器是会照着纸一条条干活的人。换一个人（不同版本/不同安装的 Python）读同一张纸，可能步骤一样，也可能因为他的「工具箱」（已装的包）不一样而卡住。所以不仅要问「纸上写了什么」，还要问「现在是谁在读」—— 用 `sys.executable` 问。
